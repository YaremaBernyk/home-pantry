# Правила роботи над Home Pantry

Цей файл містить інструкції для агентів, які працюють у цьому проєкті. Прямі вказівки користувача мають пріоритет. Перед змінами прочитай відповідні файли й збережи наявні зміни користувача.

## Стек і призначення

- Flutter і Dart; обмеження Dart у `pubspec.yaml`: `^3.13.3`.
- Інтерфейс побудовано на Material із власними кольорами та спільними віджетами.
- Основна ціль лабораторної — вебзастосунок Home Pantry для обліку продуктів.
- Залежності: Flutter SDK і `cupertino_icons`. Перевірки: `flutter_test`, `flutter_lints`.
- Поточний етап — лабораторна №3: desktop-інтерфейс за макетами лабораторної №2, демонстраційні дані та переходи між екранами.
- Реальну авторизацію, надсилання листів, збереження даних, Firebase та REST API на цьому етапі не підключати без окремого завдання.
- Адаптивний інтерфейс — наступний етап. Орієнтир ширини 360 px є припущенням про «чверть екрана», а не підтвердженою вимогою викладача.

## Структура

- `lib/main.dart` — запуск, тема, маршрути `/login`, `/register`, `/reset`, `/home`.
- `lib/screens/auth_screen.dart` — вхід, реєстрація, відновлення пароля.
- `lib/screens/home_screen.dart` — Dashboard, інвентар, профіль і діалог додавання продукту.
- `lib/core/widgets/pantry_widgets.dart` — спільні поля, кнопки, картки й кольори.
- `assets/` — ресурси, які реєструються в `pubspec.yaml`.
- `test/widget_test.dart` — перевірки навігації та відображення desktop-екранів.
- `web/`, `android/`, `ios/`, `windows/`, `macos/`, `linux/` — платформи Flutter.
- `flutter/` усередині проєкту — копія Flutter SDK, а не код застосунку. Не редагувати її під час роботи над екранами; не виконувати рекурсивне форматування чи аналіз усього кореня, які можуть зачепити SDK.

## Команди

Виконувати з кореня проєкту у PowerShell. Команди нижче передбачають справний Flutter SDK у PATH. Якщо `flutter` не знайдено, використати повний шлях до перевіреної інсталяції; не встановлювати й не оновлювати SDK автоматично.

```powershell
# Перевірка середовища й доступних пристроїв
flutter --version
flutter doctor
flutter devices

# Отримання залежностей
flutter pub get

# Запуск вебверсії
flutter run -d chrome

# Альтернативний запуск локального вебсервера
flutter run -d web-server --web-port 8080

# Форматування тільки коду застосунку та тестів
dart format lib test

# Аналіз тільки коду застосунку та тестів
flutter analyze lib test

# Тести
flutter test

# Збірка вебверсії; результат у build/web/
flutter build web --release
```

За наявності налаштованого середовища Windows можна використовувати `flutter run -d windows` та `flutter build windows --release`. Для поточного вебзавдання перевірка Windows-збірки не обов’язкова.

Не запускати `flutter clean`, `flutter pub upgrade` чи встановлення нових залежностей без конкретної потреби. `flutter pub get` і перший запуск можуть потребувати мережі та запису в кеш SDK.

## Правила коду

- Дотримуватися `analysis_options.yaml` і `flutter_lints`; не вимикати правила, щоб приховати помилки.
- Використовувати `dart format`, імена класів у PascalCase, змінних і методів у lowerCamelCase, файлів у snake_case.
- Використовувати `const`, де можливо, та null safety; уникати необґрунтованих `!` і `dynamic`.
- Спільні елементи інтерфейсу зберігати в `lib/core/widgets/`. Нові великі екрани виносити в окремі файли в `lib/screens/`.
- Використовувати `StatelessWidget`, якщо локальний стан не потрібний. Зміни стану виконувати через відповідний механізм Flutter.
- Метод `build()` має описувати інтерфейс: не читати файли, не виконувати мережеві запити й не запускати складні обчислення всередині нього.
- Зберігати дизайн макетів: світлий фон, теракотові акценти, бічне меню, відступи й ієрархію тексту. Мова інтерфейсу — англійська, пояснення користувачу — українською.
- Не замінювати екран суцільним зображенням макета: поля, кнопки й навігація мають бути віджетами.
- Демонстраційні кнопки можуть відкривати екрани або пояснювати, що серверна дія не підключена. Не показувати неправдиве повідомлення про надісланий лист чи збережений пароль.
- Контролери й інші ресурси, якщо вони додаються, звільняти в `dispose()`.
- Не змінювати згенеровані файли в `.dart_tool/`, `build/` або Flutter SDK вручну. Не додавати паролі, токени чи локальні абсолютні шляхи в код застосунку.
- Не публікувати проєкт і не надсилати запрошення викладачу без прямого дозволу користувача.

## Самоперевірка

1. Перевірити перелік змінених файлів і переконатися, що зміни стосуються завдання. Якщо репозиторій налаштовано, використати `git diff --check` і `git diff`.
2. Виконати `dart format lib test`, `flutter analyze lib test` і `flutter test`. Для зміни інтерфейсу або навігації додати чи оновити змістовний тест; для правок документації запуск Flutter не потрібний.
3. Для завершення вебреалізації виконати `flutter build web --release` та перевірити запуск у браузері.
4. На поточному desktop-етапі перевірити вікно 1440 × 1025: відсутність overflow, обрізаного тексту й недоступних кнопок. Зображення з попереднього звіту мають розмір 1440 × 1024; різниця в один піксель не потребує окремого дизайну.
5. Перевірити вхід → Dashboard; переходи до реєстрації й відновлення пароля та назад; Dashboard → Pantry → Profile; відкриття й закриття діалогу; вихід із профілю. Поля паролів мають приховувати введений текст.
6. Порівняти екрани з макетами. Для звіту використовувати скриншоти реально запущеного застосунку, а не зображення Figma, видані за результат реалізації.
7. Коли почнеться адаптивний етап, перевірити узгоджені розміри, включно з вузьким екраном: перебудову меню й карток, прокручування та відсутність горизонтального переповнення. Не вважати масштабування всього desktop-екрана адаптивністю.
8. У підсумку вказати, що змінено, які перевірки пройшли та що залишилося неперевіреним. Якщо середовище не запускається, навести фактичну причину й не стверджувати, що тести або збірка успішні.
